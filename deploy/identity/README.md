# Private meetings and workspace administration

The current deployment preference requires an India-hosted identity service. Use [the self-hosted Keycloak setup](SELF_HOSTED.md). The Auth0 instructions below describe the optional existing adapter and are not the selected deployment.

## What people see

A shared link opens the sign-in screen. After verifying their email through the identity provider, a guest can ask to join. The host sees the verified address and chooses Admit or Deny. Only an approved guest can open device setup and obtain a room or media credential. The microphone and camera start off. A declined request stays declined for that room. Leaving normally allows a new request. A guest switching devices can disconnect their previous membership and ask the host to admit the new one. A copied code is safe to forward in the sense that possession alone never grants admission.

Only one designated email can create new meetings. Each room records the account that created it. Changing the designated email affects future meetings. During a translated meeting the speaker can choose **Correct for everyone**, for example to change “Room 14” to “Room 40.” The correction is a new message sent through the translation pipeline. Earlier confirmations remain attached to the earlier wording. People present for the correction can acknowledge its new version. A failed translation is visible. In scripted mode only listed sample translations are available. Raw audio mode carries original speech and has no generated transcript.

> Historical Auth0 configuration below is an alternative setup, not the current hosted identity service. Charcha's deployed identity is Keycloak in Delhi with Google/password sign-in. See [current operating instructions](../../docs/ON_DEMAND_MEETINGS.md). Do not create an Auth0 tenant to use the existing deployment.

## Configure an alternative Auth0 deployment

1. Create an Auth0 tenant in a region you approve for identity data. Choose **Regular Web Application**, RS256 ID token signing and a token endpoint authentication method of **POST** (client secret in the request body). Enable Authorization Code. Charcha exchanges the code on the server and uses PKCE, state and nonce. Keep the application secret on the server.
2. Enable a database connection for email/password registration and verified email delivery. Enable the Google social connection on this application and supply your own Google OAuth client for production. Configure its authorized redirect URI from the Auth0 Google connection instructions. The Google-to-Auth0 callback differs from the Auth0-to-Charcha callback. Configure email delivery and verify a real test address.
3. Register the exact app callback, for example `https://meet.your-domain.in/api/account/callback`. Set the web origin to `https://meet.your-domain.in`. For a laptop trial, configure a separate application with the same callback path at `http://localhost:5180`, or your trusted LAN HTTPS address. Use that exact hostname in both the browser and server settings.
4. Provision an administrator in a database connection with username authentication enabled. Require a strong password, verify the email, enroll an authenticator and keep recovery material with the operator. Record the immutable Auth0 user ID beginning with `auth0|`. Enable Auth0 attack protection and MFA with OTP and **Customize MFA Factors using Actions**. Install the two Post Login Actions in order from this folder, first `admin-challenge.js`, then `admin-claim.js`. Each Action needs its own `CHARCHA_CLIENT_ID` and `CHARCHA_ADMIN_SUBJECT` settings matching the server. Check tenant feature availability and pricing before activation. Access fails closed if the MFA claim, verified email, identity or fresh authentication is absent.
5. Fill the private server environment from the identity section in `server/.env.example`. The domain is the tenant host without a scheme. `CHARCHA_MEETING_HOST_EMAIL` is the single address allowed to create rooms. `CHARCHA_ADMIN_CONNECTION` is the exact database connection name. The admin and meeting host may be different people. To change the admin, revoke the old identity in Auth0, update the server setting and Action secrets, then restart the API to invalidate existing app sessions.
6. Open `/#/admin` to sign in with the administrator username, password and second factor. Administrator access lasts at most 15 minutes. The portal shows active meetings and waiting counts, and lets the administrator change the designated host. Host changes are stored in `accounts.sqlite3` next to the usage database. Preserve the data volume. The latest 100 changes are retained and the portal lists the ten most recent. Application sign-out invalidates the app session and removes associated room memberships.

## Deployment order

1. Agree the DNS names, hosting region, identity provider terms, cost ceiling, designated host and administrator. Keep actual secrets in the private server environment or secret manager. Identity sign-in uses an external provider. Indian residency for identity and meeting media must be established separately.
2. Prepare the Linux VM, DNS, TLS and UDP networking using the production guide. Run the offline configuration generator and static checks in that guide. They do not start the stack. For a LAN trial add the identity settings to its **private generated api.env**, with the LAN URL as the public origin, before starting that stack. Existing anonymous room probe scripts need an authenticated account and host admission to exercise secured routes. Use one API worker. Meetings, waiting requests, sign-in flows and sessions are ephemeral and a restart ends them.
3. Pause for the owner's explicit deployment approval. On the approved host only, run the production start script and then check HTTPS, the callback and media connectivity. Start in a controlled environment. The provider approval window remains a separate, explicit decision.
4. Acceptance requires three independent browser profiles. Sign in as the designated host, create a meeting and share its link. In two guest profiles verify distinct emails, ask to join and keep devices off. Admit one, deny the other, test session expiry/sign-out and attempt direct access to the same room and admin page from the denied profile. In a separately approved interpreted call, correct a time or number, acknowledge the correction and check the recap on both devices. Also check OTP failure and account recovery with the real tenant.
